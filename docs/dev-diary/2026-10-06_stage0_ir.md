# Stage 0

Variables can change now. And the compiler no longer generates code from the parser's tree.

Yesterday the compiler learned to say no. Today it learned two additional things:
that a variable can be assigned after it is declared, and the code generator should not be reading
the parser's AST at all.

I started with the spec, because I did not want to implement assignment against a vague paragraph.
The old section said assignment "may" be supported and recommended postponing it until the IR
layer exists. I rewrote it. Locals and parameters are mutable, assignment is a statement and not
an expression, and the target has to be a parameter or local that is already declared.
Assignment never declares anything. The grammar got a new `assignment-statement` rule.

The implementation was small. The parses needed one token of lookahead: an identifier followed
by an `=` is an assignment, anything else is still an expression statement.
The semantic analyzer checks that the target exists, and that the value is an `int`.
The code generator evaluates the right side and stores `%eax` into the variable's slot.

Then I allowed declarations without an initializer, so `int x;` is valid now. The parser just makes
the `=` optional, and the code generator has nothing to emit for it since the slot is reserved in
the prologue anyway.

The interesting part is that this makes reading an uninitialized variable possible, and that has
to be an error. The analyzer now keeps a second set next to the set of declared names:
the variables that are definitely initialized. Parameters start in it. A declaration with an
initializer adds its variable, and so does an assignment. Reading a variable that is declared
but not in the set gives

```text
semantic error at 4:18: variable used before initialization: x
```

This ins only correct because JAOT0 has no control flow. With straight-line code, "assigned
earlier in this method" is the same as "assigned on every path". Once `if` exists, an assignment
inside one branch must not count, so this set will have to become real flow analysis. It is the
same situation as the return check from yesterday, where the simple version is right today and I
already know where it will break.

Then came the actual goal of today, the IR.

The code generator used to take the parser's `Program` directly. That means it had to know about
names, about `StmtKind::VarDecl` versus `StmtKind::Assignment`, and about whatever else the
parser decides to do to the source. It also had its own map from variable names to stack
offsets. That is fine for one x86 backend. It is not fine if there should ever be a second one.

So there is now `jaot/ir.h` and a lowering pass between the semantic analyzer and the code generator

```text
lexer -> parser -> semantic analyzer -> IR lowering -> code generator
```

The IR is deliberately small:

- every local, parameters included, is a `Local` with aa numeric `LocalId`, a name, a type and
  a flag for being a parameter
- expressions are `Integer`, `Local`, `Binary` and `Call`, and every one of them carries a `Type` and a `SourceLocation`
- statements are `AssignLocal`, `Evaluate` and `Return`

Names are gone after lowering. A variable read is a `Local` expression with an id, and the code
generator keeps a map from id to stack offset instead of a map from string to offset.
A declaration with an initializer and a plain assignment become the same thing, `AssignLocal`,
because to a backend they are the same operation. A declaration without an initalizer disappears
completely, since its slot is already part of the method's locals. The lowerer also
resolves call targets to their return types, so `printInt` is a `void` call and everything
else gets the type of the method it calls.

The code generator shrank a bit and got more suspicious. Everything that used be guranteed by the
parser is now a defensive check against a malformed IR: a binary expression without a right side,
an assignment without a value, a parameter without a slot. The six-parameter limit moved into
the generator's prologue and call code as well, since it is a limit of the calling convention
and not of the language. While I was in there I fixed two small things I had been ignoring:
a stray space after `@function` in the `.type` directive, and the assignment emitting `mov`
where everything else emits `movl`.

I want to be honest about what this IR is not. It is still a tree, not three-address code.
The generator still evaluates it with the same push, pop and `%eax` strategy, and it still emits
x86-64 System V directly. The division checks and the stack alignment still live in the generator.
So today the IR does not make aynthing faster or more portable by itself. What it does is draw
the line. The frontend now ends at the IR, and the backend starts there. The next step
is to move the target-specific parts behind a proper backed interface,
and only then does an ARM64 generator make sense.

All the existing tests pass unchanged, which is exactly what I wanted from a refactor like this.
The generated assembly for the old programs is the same except for the `movl` fix.
